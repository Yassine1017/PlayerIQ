# Authenticated GPS report ingestion

## Phase 2 flow

```text
verified Supabase user
  → bounded multipart PDF validation (extension, MIME, magic, layout, SHA-256)
  → private Supabase Storage object + report_uploads + ingestion_jobs
  → worker claims due job with PostgreSQL SKIP LOCKED
  → ActivityReportPdfV1Adapter.detect / extract
  → RawReport / RawAthleteRow / RawMetricObservation
  → ReportValidator.validate
  → activity_reports / source_athlete_rows / source_metric_observations / ingestion_findings
  → uploader reviews candidate rows at GET /v1/report-uploads/{id}
  → uploader explicitly confirms an eligible own row or authorized team member row
  → optional durable source identity and one accepted session per confirmed link
  → accepted player_sessions + validated session_metric_values with source observation IDs
```

The API reads at most `MAX_UPLOAD_BYTES + 1` bytes and rejects larger files (10 MiB default). A filename is display-only; storage keys contain the verified uploader UUID and a generated UUID. The API checks an uploader-scoped SHA-256 duplicate before storage and the database enforces a partial unique index. It stores the object privately, then creates the upload and job in one database transaction. If that transaction fails, it attempts to delete the uploaded object; an operator must reconcile any private orphan if cleanup also fails. No browser receives a permanent public object URL.

The API role has `INSERT`, but no `SELECT` or `UPDATE`, on `ingestion_jobs`. Its insert policy permits a job only for an upload owned by the transaction's verified actor. Enqueueing uses a no-return insert with a generated UUID so PostgreSQL does not require `SELECT` for SQLAlchemy's implicit `RETURNING` of server defaults. The worker alone reads, claims, and updates jobs. A database enqueue failure rolls back the upload row, attempts private-object cleanup, logs only an exception type and SQLSTATE, and returns a controlled upload error. No grant or policy migration is needed for this correction.

`python -m app.cli.process_ingestion --limit N` runs a bounded worker pass. The worker uses a separate restricted database login, claims due jobs with `FOR UPDATE SKIP LOCKED`, and can reclaim stale `extracting` locks. It verifies stored bytes against the upload SHA-256, then writes extraction, validation, and findings atomically. A report already persisted is not reinserted. Transient failures retry with bounded backoff and end in a safe rejection after three attempts. An unsupported layout is rejected with a finding; it never creates partial player sessions. A bad athlete row stays isolated from valid rows.

`IngestionService.inspect_pdf` remains a side-effect-free entry point with a 25 MiB intrinsic limit. The upload boundary is stricter by default. Its single adapter recognizes the reviewed five-page, selectable-text Activity Report layout. It extracts activity metadata, candidate athlete rows, table metrics, and report-level averages. The synthetic test document has 12 rows, but the parser does not assume the real roster size. It preserves source labels, raw strings, units, parsed values, page/row locators, parser version, and scope.

Page-2 `Player Load` and `Maximum Velocity` labels are extracted in the normal worker pass. The adapter first checks PDF text objects and positional columns. The reviewed layout places these labels in a raster chart image, with no useful vector label structure, so it falls back to bounded **local** OCR on that page's chart image. It reads printed numeric labels, never bar heights. Exact, unique source-label matching associates chart athletes with source rows within the same report; a name never links to a PlayerIQ account. OCR requires a regular labelled chart layout, a unique row match, high numeric confidence, valid metric-specific numeric form, and agreement between two scales to accept a label. Low-confidence/malformed labels remain review evidence; unextractable labels remain **missing**, never zero. Table values survive chart failure. The adapter does not infer athlete duration, session type, timezone, speed thresholds, participation, or identity. `Overall (%)` remains source evidence and is excluded from accepted analytics because its definition is unresolved. Source-specific values carry comparability keys that remain unverified until provider definitions are supplied.

Validation maps known athlete labels through `metrics_v1`, checks numeric integrity and units, and returns candidate normalized values. `ready` means no blocking row finding; `accepted` marks a usable metric; `zero_recorded` does not prove participation; `needs_review` holds suspicious values; `missing` records unavailable chart data. The configurable 45 km/h maximum-velocity review value and three-times-peer-median distance check are review heuristics, never corrections or provider thresholds. All anomalies retain original source values.

The uploader-only status response includes activity metadata, each candidate's source name/position, source observations, missing labels, quality state, existing links, and scoped identity-recognition state. A source label is never compared to an account display name. First-time “This is me” confirmation or team-manager confirmation repeats the exact printed label and records a durable mapping only after the existing link validator accepts the row. A future exact scoped mapping marks a row recognized, but **does not create a session**; the uploader confirms the link. The link transaction checks uploader ownership, owned-player or manager/member authorization, row membership, upload state, eligibility, duplicate links, and same-player/date conflicts. It revalidates stored observations and copies only accepted athlete metrics with source IDs. Team averages, missing or held chart metrics, and activity duration are never promoted as player values. `zero_recorded` and row-level `needs_review` return a review-required error. Repeating the same accepted link is idempotent. See [PLAYER_IDENTITY.md](PLAYER_IDENTITY.md).

Phase 4 adds an uploader-only `GET /v1/report-uploads?limit=&cursor=` list for the frontend's recent upload history. It returns filename, status, creation/processing time, error code, and row count after processing; it does not expose candidate rows. The web client polls a single report every five seconds only while it is received, queued, extracting, or validating. Phase 5.5 adds optional manager-only team upload/assignment and explicit source identity confirmation. Existing private reports can be assigned to a team only by their uploader-manager and only when all existing linked players are team members. Duplicate upload protection is unchanged.

The raw PDF and unlinked teammate rows remain available only to the uploader. Ordinary player-session endpoints expose only accepted linked metrics, row-specific warnings, date/type/quality, and provenance IDs. A linked player does not gain access to the team PDF. Full authentication and role details are in [AUTH.md](AUTH.md).

## Phase 3 chart-label review

Phase 5.6 adds guided frontend selection without changing ingestion or acceptance. The dashboard leads to an authorized processed report (or report picker), compact self-selection cards, and explicit source-evidence confirmation. The existing Phase 5.5 transaction remains authoritative. After linking, the client verifies an owned connected identity and returns to the dashboard, which reloads accepted history. Ineligible rows do not establish partial identities; future recognized rows still require explicit session confirmation. See [PLAYER_IDENTITY.md](PLAYER_IDENTITY.md) for the guided flow and verification limits.

Automatic extraction uses the existing `source_metric_observations` records: report/upload and source-row foreign keys, exact raw label, parsed decimal, `p2` chart and bounding-box locator, `method:pdf_position` or `method:ocr`, confidence/deterministic state, parser version, and accepted/review/missing quality state. It requires no migration. Only the uploader can view all candidate chart observations. A linked player sees only accepted metrics for their own session and its limited provenance. The uploader can open the private PDF, identify a ready source row by UUID and ordinal, and submit a missing, uncertain, or corrected printed label to `POST /v1/report-uploads/{id}/chart-reviews`. This creates a `proposed` review only. The uploader then confirms via `POST /v1/report-uploads/{id}/chart-reviews/{review_id}/confirm`; the request must repeat both source athlete row UUID and raw label. `GET /v1/report-uploads/{id}/chart-reviews` lists uploader-only history. Another account cannot access these routes, even if linked to a player in the report.

Confirmation creates a separate athlete-scoped source observation with a page-2 chart locator and reviewer audit; the automatic observation remains as provenance. A non-suspicious confirmation becomes authoritative for an existing linked session, or is copied when that row is linked later. A correction supersedes the prior confirmed review and replaces the accepted metric source observation. Repeating confirmation is idempotent. A speed label above the configured review value is kept as `held`; it removes any previously accepted top-speed value for that row until supported evidence is available. Neither the original PDF nor a chart rendering is stored in the repository. There is no general OCR pipeline or bar-height estimation. Existing completed uploads are not automatically backfilled; this worker change applies when a report is newly processed.

Accepted history is projected by the analytics repository, then calculated by pure `analytics_v1` domain functions, then orchestrated by a reusable service. A post-link correction changes the history fingerprint, marking previously saved AI analyses stale. The analytics HTTP routes expose overview, trend, and workload outliers. The Phase 5 read-only AI tools call the same service for latest-versus-five, personal record, hardest training session, last speed exceedance, change calculations, and accepted session facts; see [AI_ANALYST.md](AI_ANALYST.md).

## Known limits

Only the reviewed Activity Report adapter is implemented. Scanned PDFs, arbitrary GPS providers, CSV, OCR of other layouts/charts, manual resolution of anomalous readings, and deletion/retention workflows are later work. The OCR region and regular-column geometry are specific to this supported chart layout; unreadable or ambiguous labels remain for manual review. Source display names can contain PDF line-wrap artifacts and must never be used as account identity keys. Migration `0009_player_identity_teams` adds identity/team provenance and team scoping; it does not reprocess completed uploads or backfill identity mappings. All committed fixtures are synthetic.
